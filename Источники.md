### 1. QuiCK: A Queuing System in CloudKit

Kfir Lev-Ari и др., ACM SIGMOD, 2021. [Ссылка](https://www.foundationdb.org/files/QuiCK.pdf)

**О чём статья.** Авторы описывают, как Apple встроила очередь фоновых задач в CloudKit. Основной вопрос для НИР — как связать постановку задачи с изменением данных, от которого эта задача зависит.

**Подход.** QuiCK использует FoundationDB как общее транзакционное хранилище для пользовательских данных и задач. Если изменение данных требует фоновой обработки, приложение записывает изменение и задачу в одной транзакции.

![[Pasted image 20261124092538.png|480]]

**Значение для НИР.** QuiCK представляет подход, в котором очередь встроена в хранилище прикладных данных. Статья позволяет выделить две разные гарантии: **атомарную постановку** задачи вместе с изменением данных и выполнение с семантикой at-least-once, при которой задача может выполниться повторно.

### 2. Kafka versus RabbitMQ: A Comparative Study of Two Industry Reference Publish/Subscribe Implementations

Philippe Dobbelaere, Kyumars Sheykh Esmaili, ACM DEBS, 2017. [Ссылка](https://doi.org/10.1145/3093742.3093908)

**О чём статья.** Авторы сравнивают архитектуру Kafka и RabbitMQ, включая хранение сообщений, порядок доставки и подтверждения. В рассмотренных моделях RabbitMQ учитывает подтверждение отдельных сообщений, а группа потребителей Kafka отслеживает позицию чтения в партиционированном журнале.

**Значение для НИР.** Статья помогает объяснить, как модель хранения и учёта прогресса влияет на повторную доставку и возможность перечитать обработанные сообщения. Сравнение описывает реализации 2017 года. При анализе современных версий необходимо указать используемый режим потребления.

### 3. Netherite: Efficient Execution of Serverless Workflows

Sebastian Burckhardt и др., _Proceedings of the VLDB Endowment_, 2022. [Ссылка](https://www.vldb.org/pvldb/vol15/p1591-burckhardt.pdf?utm_source=chatgpt.com)

**О чём статья.** Авторы представляют движок для надёжного выполнения многошаговых процессов в Azure Durable Functions. Netherite сохраняет изменения состояния в журнале и может зафиксировать прогресс нескольких шагов одной операцией записи.

**Значение для НИР.** Дополнительный источник для сценариев с зависимыми шагами. Он показывает, какое состояние нужно сохранить, чтобы после сбоя продолжить процесс с учётом уже зафиксированных результатов, и как групповая фиксация сокращает число записей в хранилище.

## Препринты

### 4. DBLog: A Watermark Based Change-Data-Capture Framework

Andreas Andreakis, Ioannis Papapanagiotou, arXiv, 2020. [Ссылка](https://arxiv.org/abs/2010.12597)

**О чём работа.** Авторы описывают систему CDC, которая совмещает чтение журнала транзакций со снятием снимка таблиц. Это позволяет получить исходное состояние данных и поступающие изменения, даже если журнал хранит только ограниченную историю.

**Значение для НИР.** Дополнительный источник о механизмах CDC на основе журнала транзакций. Помогает объяснить, какую роль выполняют журнал и снимок данных при чтении изменений из БД.

## Книги

### 5. Microservices Patterns

Chris Richardson, Manning, 2018, глава 3. [Ссылка](https://www.oreilly.com/library/view/microservices-patterns/9781617294549/OEBPS/Text/03.html)

**О чём глава.** Автор разбирает проблему двойной записи, возникающую, когда приложение изменяет данные в БД и публикует сообщение в отдельный брокер. _Transactional Outbox_ позволяет сохранить запись о будущей публикации вместе с прикладным изменением. _Polling Publisher_ и _Transaction Log Tailing_ описывают два способа передачи этой записи в брокер.

**Значение для НИР.** Источник даёт терминологию для сравнения двух вариантов outbox. Локальная транзакция обеспечивает атомарную запись, а способ доставки определяет, как сохранённое сообщение попадёт в брокер.

### 6. Designing Data-Intensive Applications

Martin Kleppmann, O’Reilly, 1-е изд., 2017. [Ссылка](https://www.oreilly.com/library/view/designing-data-intensive-applications/9781491903063/)

**О чём материал.** В главе 7 _Transactions_ рассматриваются атомарность и изоляция транзакций. Глава 11 _Stream Processing_ посвящена системам обмена сообщениями, партиционированным журналам, CDC и отказоустойчивости обработки потоков.

**Значение для НИР.** Глава 7 даёт теоретическую основу для атомарной постановки задачи вместе с изменением данных. Глава 11 помогает сопоставить способы хранения сообщений, учёта прогресса потребителей и повторной обработки.

## Инженерные статьи

### 7. FOQS: Scaling a Distributed Priority Queue

Meta Engineering, 2021. [Ссылка](https://engineering.fb.com/2021/02/22/production-engineering/foqs-scaling-a-distributed-priority-queue/)

**О чём статья.** Meta описывает FOQS — распределённую очередь для фоновых задач нескольких микросервисов. Записи задач хранятся в шардированном MySQL, а приложения взаимодействуют с очередью через API отдельного сервиса.

**Значение для НИР.** FOQS показывает, как очередь на реляционной БД может быть самостоятельным сервисом. Вместе с River этот пример позволяет сравнить два размещения очереди: в БД приложения и в хранилище отдельного сервиса.

### 8. High Availability by Offloading Work Into the Background

Shopify Engineering, 2021. [Ссылка](https://shopify.engineering/high-availability-background-jobs)

**О чём статья.** Shopify рассматривает применение transactional outbox к фоновым задачам. Приложение сохраняет параметры задачи вместе с прикладными данными, а отдельный процесс опрашивает промежуточную таблицу и передаёт задачу в рабочую очередь.

**Значение для НИР.** Статья разбирает сбой между публикацией задачи и сохранением отметки о публикации. Если задача уже попала в очередь, а отметка не сохранилась, следующая попытка может поставить её повторно. Этот сценарий позволяет отдельно рассмотреть надёжность публикации и повторное выполнение задачи.

### 9. Reliable Microservices Data Exchange With the Outbox Pattern

Gunnar Morling, Debezium, 2019. [Ссылка](https://debezium.io/blog/2019/02/19/reliable-microservices-data-exchange-with-the-outbox-pattern/)

**О чём статья.** На примере сервиса заказов автор показывает, как сохранить прикладное изменение и событие в одной транзакции PostgreSQL. После фиксации Debezium считывает изменение из журнала и передаёт сообщение в Kafka.

**Значение для НИР.** Статья даёт конкретную архитектуру transactional outbox с CDC. Её можно сопоставить со схемой Shopify: запись outbox в обоих случаях создаётся в прикладной транзакции, а дальнейшая доставка строится либо на чтении журнала, либо на опросе таблицы.

## Документация

### 10. River: Transactional Enqueueing

Документация River. [Ссылка](https://riverqueue.com/docs/transactional-enqueueing)

**Что рассматривается.** На примере создания пользователя показано, как поставить задачу в очередь River в той же транзакции PostgreSQL, которая сохраняет данные пользователя. Документация объясняет, какие сбои возможны при отдельной записи данных и постановке задачи.

**Значение для НИР.** River даёт пример хранения и обработки очереди на реляционной БД приложения. Его можно использовать как реализацию атомарной постановки задачи на PostgreSQL.

### 11. Debezium: PostgreSQL Connector

Документация Debezium. [Ссылка](https://debezium.io/documentation/reference/stable/connectors/postgresql.html)

**Что рассматривается.** Документация описывает получение изменений из журнала PostgreSQL (WAL), восстановление позиции чтения после сбоя и удержание WAL при отставании коннектора.

**Значение для НИР.** Источник позволяет сравнить опрос таблицы и CDC по тому, какую работу выполняет БД, как восстанавливается доставка и какие компоненты нужно обслуживать.

### 12. Debezium: Outbox Event Router

Документация Debezium. [Ссылка](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)

**Что рассматривается.** Документация показывает, как Debezium преобразует изменение строки outbox в сообщение Kafka и определяет его топик, ключ и идентификатор события.

**Значение для НИР.** Источник уточняет границу ответственности компонентов: коннектор получает изменение из PostgreSQL, маршрутизатор формирует сообщение для Kafka, а потребитель отвечает за обработку полученного сообщения.
